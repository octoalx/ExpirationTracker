## Что изменится для вас

Если загрузить один и тот же файл дважды (или файл, где часть товаров уже есть в
таблице), второй раз товары не удвоятся. В окне импорта будет видно, сколько
товаров добавлено, а сколько уже было. Товар с тем же штрихкодом, но другой датой
годности по-прежнему добавляется отдельной строкой — это разные партии.

## Problem

`POST /api/products/import` создаёт строку на каждую запись файла без проверки,
что такая строка уже есть в отделе: `src/pages/api/products/import.ts` вызывает
`tx.product.create()` в цикле и не делает ни одного запроса на существование.
Ограничения уникальности в схеме нет намеренно (`barcode` без `@unique` в
`prisma/schema.prisma`, комментарий «чтобы не блокировать добавление одинаковых
товаров»), поэтому повторная загрузка молча удваивает таблицу.

Это записано как открытый вопрос №5 в `memory-bank/activeContext.md` («Excel import
is create-only, so a repeated upload creates duplicates»).

Механизм: отсутствие проверки на дубликат в транзакции импорта, а не ошибка в
парсере — парсер и валидация (`validateInventoryProducts`) работают корректно.

## Acceptance criteria

- AC1 — повторная загрузка того же набора не создаёт новых строк для товаров,
  которые уже есть с тем же штрихкодом и той же датой годности; ответ содержит
  число созданных и число пропущенных как уже существующие.
- AC2 — товар с тем же штрихкодом и **другой** датой годности создаётся отдельной
  строкой (партии не склеиваются).
- AC3 — если у существующей строки и у загружаемой указано количество, количества
  складываются; если количество не указано хотя бы с одной стороны, количество
  существующей строки не меняется.
- AC4 — импорт остаётся одной транзакцией: при любой ошибке не создаётся ни одной
  строки, и частичного дублирования не остаётся.
- AC5 — окно импорта показывает оба числа («Импортировано N, уже было M»), а не
  только количество созданных.

## Решения, которые нужны от вас

1. **Что считать дубликатом.** Предлагаю: одинаковый штрихкод **и** одинаковая дата
   годности внутри одного отдела. Тогда тот же товар с другой датой — отдельная
   партия. Альтернатива — считать дубликатом только по штрихкоду (тогда разные
   партии склеятся и потеряют даты).
2. **Что делать при совпадении.** Предлагаю: прибавить количество, если оно
   указано с обеих сторон, иначе оставить как есть; в обоих случаях товар не
   создаётся и попадает в число «уже было». Альтернатива — не менять количество
   никогда и только пропускать.

Если согласны с обоими предложениями — достаточно написать APPROVED.

## Out of scope

- Ручное добавление (`POST /api/products`) и добавление по сканеру не меняются:
  там дубликат — осознанное действие пользователя.
- Схема и миграции не меняются: `@unique` на штрихкод не добавляется.
- Поведение импорта в части разбора файла (формат, пятая колонка) не меняется —
  это отдельная задача из списка открытых вопросов.
- Общий справочник штрихкодов и каталог не затрагиваются.

## Risks and invariants

- Скоуп — отдел вызывающего: поиск совпадения обязан идти по `storeId`
  из `inventoryScope`, иначе импорт увидит чужую таблицу.
- Данные не удаляются и не перезаписываются: только пропуск создания и (по
  решению №2) сложение количества.
- Граница «одна и та же дата» сравнивается по календарной дате, а не по времени:
  даты импортируются как `T00:00:00.000Z`.
- Транзакция сохраняется: ни одна строка не создаётся при ошибке.
- Отчёт в окне не должен выглядеть как ошибка, когда часть строк пропущена.
